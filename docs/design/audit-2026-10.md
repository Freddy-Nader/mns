# Design audit — October 2026

An audit of the built Next.js site (`components/`, `app/globals.css`) against two lenses, plus a check of the docs against the code:

- **apple-design**: response on press, spatial consistency, wayfinding, materials, typography, reduced motion, accessibility (`.claude/skills/apple-design`)
- **emil-design-eng**: animation decisions, easing and duration, press feedback, hover on touch, performance (`.claude/skills/emil-design-eng`)

Screens were checked at 1440×900 and 390×844 against `next start`. Nothing here changes the direction set in [ADR-0003](../adr/0003-visual-direction-peso-y-lista.md). Most findings are craft details beneath it.

## What already holds up

Several things already meet both lenses and should stay as they are:

- **No decorative motion.** The hero and sections have no entrance animations, and nothing animates on a keyboard action. Every transition names its properties (there is no `transition: all`) and none uses `ease-in`.
- **The bio reveal is built the way Apple builds motion.** It eases from the current value toward the scroll target (exponential approach, 0.35 s), so it can be interrupted at any frame, it sleeps when it has caught up, and it never starts under reduced motion.
- **Solid vs. outline is a real rule, used the same way everywhere.** That is the Familiarity principle: things that look the same behave the same.
- **Wayfinding by task.** Short, specific nav labels (*Fechas*, not "Próximas fechas"), and every route ends in a named contact.
- **Spacing and alignment you can defend.** Day labels sized in `em` so events share an x, the 1fr/auto/1fr header grid, and CTAs with equal widths.

## Findings

Ranked by how much each affects real visitors. The format is Emil's Before / After / Why.

### 1. Bugs on touch devices and accessibility failures

| Before | After | Why |
| --- | --- | --- |
| 18 `:hover` rules, none behind a media query (`globals.css` `.btn:hover`, `.btn--ghost:hover`, `VideoShowcase` `.item:hover`, `.poster:hover .play`) | Wrap them in `@media (hover: hover) and (pointer: fine)` | On iOS and Android a tap leaves hover applied. After a tap on *Cómo llegar* the outline pill **stays solid black** when the visitor comes back to the tab, and video thumbnails stay in colour. On a phone, the solid/outline rule breaks. |
| `--on-dark-dim: #6E6E6B` on `#0A0A0A` = **3.87 : 1** | `#8A8A87` (5.72 : 1) or `#939390` (6.43 : 1) for text | Fails WCAG AA for text under 18 px. It is used 13 times for real text: footer bar (13 px), menu footer links, `.label` on dark (12 px), video notes (13 px), composer lines on ink posters (14 px). ADR-0003 justifies the high contrast because concert audiences skew older. The bio's dim state is a 0.4 opacity, not this token, so the reveal is unaffected. |
| The full menu is a `div` with `hidden`. Tab moves on to the page behind the overlay | Use `<dialog>` with `showModal()`, or put `inert` on `<main>` and `<footer>` while the menu is open | Focus reaches links you can't see. `<dialog>` also handles Escape, the top layer, and returning focus, which removes most of `Menu.tsx`'s effect. |
| Footer links, social links and `ES · EN` are about 20–24 px tall | Pad each link out to a 44 px row (`padding-block` or `min-height: 44px` with inline-flex) | `tokens.md` sets a 44×44 minimum touch target. The language switch is the smallest target on the page. |
| `body { font-size: 16px }`, and every size is in px | Body `100%`, type and spacing in `rem` | Apple: respect the reader's text size. Fixed px overrides the browser's default font size, which older readers are the most likely to have raised. |

### 2. Response: buttons don't answer the press

| Before | After | Why |
| --- | --- | --- |
| `.btn` reacts only on hover (opacity 0.78) | `.btn:active { transform: scale(0.97) }`, with `transform 160ms var(--ease-out)` added to its transition list | Apple §1 and Emil both say feedback starts on pointer-down. On touch there is no hover, so today a tap gives **no feedback at all** until the page navigates. |
| Brief chips, video list items, the play disc and the burger have no pressed state | The same `scale(0.97)` on `:active` (chips, play disc). Video rows: background `--on-dark-rule` on `:active` | Every pressable element should feel heard. On full-width rows a scale looks wrong, so they get a fill instead. |
| Puertas panels: whole-panel link, no pressed state | `:active` fill one step darker (`#EAEAE7` on grey, `#1A1A1A` on ink) | A large surface shouldn't shrink. A fill confirms the tap without moving the layout. |
| No shared easing token | `--ease-out: cubic-bezier(0.23, 1, 0.32, 1)` in `:root` | Emil: the built-in `ease` is weak. One named curve for every UI transition keeps the motion consistent. |

### 3. Honest affordances

| Before | After | Why |
| --- | --- | --- |
| `.poster:hover :global(.arrow)` underlines *Solicitar* when the pointer is anywhere on a programme poster, but only the arrow text is a link | Make the whole poster the link (stretched `::after` on the arrow, as Puertas already is), **or** remove the poster-level hover | Hover promises a click target that isn't there. The featured poster has two links (dates and request), so only the eight small posters can take the stretched link. |
| The burger's span-to-× morph (`Menu.module.css`) runs underneath the opaque overlay, so nobody sees it | Delete the morph rules, or let the burger itself be the close control above the overlay | Dead motion. Apple §7: open and close are clearest when they are the same control in the same place. Today a separate `×` sits at about the same coordinates. |

### 4. The menu has no transition at all

| Before | After | Why |
| --- | --- | --- |
| `hidden` toggles the overlay: it appears and disappears in one frame | Opacity 0 → 1 in 200 ms `--ease-out` on open and 150 ms on close, using `@starting-style` + `transition-behavior: allow-discrete`. No transform | Emil's frequency table: a full menu opens occasionally, so it gets a standard animation, and exit is faster than enter. The full-screen ink jump is the most abrupt brightness change on the site (Apple §14). Opacity only, so it stays under reduced motion. |
| `document.body.style.overflow = "hidden"` | Add `scrollbar-gutter: stable` on `html` | With classic scrollbars (Windows, many Linux setups) the page shifts sideways by the scrollbar's width each time the menu opens. |

### 5. Performance

| Before | After | Why |
| --- | --- | --- |
| `.text [data-w] { will-change: opacity }` on every word of the bio (100+ spans) | Remove it, or set it from `WordReveal` only while a frame is pending | Each `will-change` can promote a compositor layer. A hundred layers for text whose opacity changes a few times per scroll costs more memory than it saves paint. |
| `WordReveal` calls `getBoundingClientRect()` on every scroll event of the page | Attach the scroll listener only while an `IntersectionObserver` reports the bio near the viewport | It forces a layout read on every scroll, everywhere on a long page, for an effect that lives in one band. |

### 6. Wayfinding: small additions

| Before | After | Why |
| --- | --- | --- |
| Anchor links jump instantly | `html { scroll-behavior: smooth }` inside `@media (prefers-reduced-motion: no-preference)` | On a 13-section page an instant jump loses the reader's sense of place. Smooth scroll shows the direction travelled. Reduced motion keeps the jump. |
| The nav doesn't show where you are | (Optional) mark the current section with `aria-current` from an `IntersectionObserver` | Apple's first wayfinding question is "Where am I?". It costs a small client component, against ADR-0005's "no JS beyond menu, player, brief". This is a decision, listed below. |

## Decisions this audit raises

These are not mine to settle, so none is applied. Each one changes `tokens.md`, `landing-page.md`, an ADR or `CONTEXT.md`:

1. **Press feedback.** `tokens.md` allows "one orchestrated effect only", and everything else is opacity/colour. Does a `scale(0.97)` press state count as a new kind of motion that the rule should name?
2. **Reduced motion.** Keep opacity/colour transitions under `prefers-reduced-motion` and remove only movement, or keep switching everything off?
3. **Dark mode.** Is the site committed to light (and the token doc is wrong), or does a viewer-level dark theme ship (and the CSS is wrong)?
4. **`--on-dark-dim`.** Raise it to pass AA (it reads less "dim"), or keep it for decoration and add a separate text token?
5. **Units.** Move the type scale and spacing to `rem`?
6. **Menu transition.** Opacity fade, or keep it instant as a deliberate hard cut that matches the hard-edged direction?
7. **Programme posters.** Whole poster clickable, or arrow only?
8. **Header material.** Apple §12 would make the sticky header translucent (`backdrop-filter`). The recommendation here is **no**: an opaque ground with a hairline is the *Peso y lista* direction. It still deserves a recorded decision, because a future agent following Apple's guidance will propose it.
9. **Section indicator in the nav.** Is it worth one more client component against ADR-0005's JavaScript budget?
10. **Glossary.** Should *Puerta*, *Encargo*, *Partitura* and *Clase / Masterclass / Curso* enter `CONTEXT.md` as defined terms? And is it time to close the open **Programa / Repertorio** question?
